# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

This is a monorepo. The Laravel application lives entirely in `deepskylog/` — run all commands below from that directory. The repo root also contains `3d-print/` (unrelated OpenSCAD/3D-print assets for physical hardware) and top-level docs (`README.md`, `Tips.md`, `CONTRIBUTING.md`).

## Commands

All commands run from `deepskylog/`.

- Install PHP deps: `composer install` (PHP 8.3 required); update with `composer update`.
- Install/build frontend: `npm install`, then `npm run dev` (Vite dev server) or `npm run build` (production).
- Format frontend/Blade: `npm run format` (Prettier with the Blade plugin, writes `resources/`).
- Format PHP: `laravel/pint` or `friendsofphp/php-cs-fixer` (config in `.php-cs-fixer.dist.php`, PSR-12 + short array syntax + alphabetized imports).
- Run tests: `php artisan test` (Pest, with `pestphp/pest-plugin-laravel`). Run a single test file with `php artisan test tests/Feature/SomeTest.php` or filter by name with `php artisan test --filter=testName`. Test env uses in-memory SQLite, sync queue, array cache/session (see `phpunit.xml`) — no external services needed. `tests/TestCase.php` binds `Tests\Support\CaseInsensitiveBlueprint`, which gives every SQLite string column `COLLATE NOCASE`, so `=` compares case-insensitively like the `utf8mb4_unicode_ci` columns on MariaDB: compare plain columns (`where('name', $v)`), not `LOWER(name) = ?`, which keeps MariaDB from using the index. An expression such as `COALESCE(a, b)` or `REPLACE(a, …)` has no collation in SQLite, so comparisons on those still need `LOWER()` on both sides.
- Rebuild search index after object data changes: `php artisan search:reindex` (TNTSearch).
- Rebuild the per-object observation statistics (`object_observation_stats`, `object_observation_stats_by_observer`: the seen/last seen columns of the object tables, via `App\Services\ObjectObservationStatistics`): `php artisan observations:rebuild-object-stats`. `ObservationObserver` keeps them up to date on model saves; code that changes `observations` with a mass update must call `ObjectObservationStatistics::refreshObjects()`, and after an SQL import or repair run the command.
- Rename observing list items to the canonical object names the list tables match on (`App\Services\ObservingListItemNameResolver`): `php artisan observing-lists:normalize-items` (dry run; add `--apply` to write, `--list=<id>` to limit). Items matching no object are only reported.
- Remove the M 1 the import of the old observing lists (April 2026) put first in about 200 lists it does not belong to (`App\Console\Commands\RemoveSpuriousListItems`): `php artisan observing-lists:remove-spurious-items` (dry run; add `--apply` to write, `-v` to list the lists). Lists whose name says M 1 belongs there (Messier, Crab, supernova remnants) are only listed; a list left empty is deleted unless it has comments, likes or subscribers. Run it after an SQL import.
- Add the member galaxies of the Hickson compact groups (`App\Console\Commands\ImportHicksonMembers`, from `database/hickson_galaxies.csv`, Hickson 1989 / VizieR VII/213): `php artisan objects:import-hickson-members` (dry run; add `--apply` to write). A member becomes the alternative name `Hickson 11A` of the galaxy with its NGC/IC/UGC name, else of the nearest galaxy within 20" (better known catalogs first), else a new galaxy `Hickson 11A`, linked to its group in `objectpartof`. Members whose galaxy is already another member are only listed.
- Repair sky values that `Magnitude` of the astronomy library rejects (`App\Console\Commands\RepairSkyValues`): `php artisan observations:repair-sky-values` (dry run; add `--apply` to write). An SQM below 10 that is a plausible NELM (2.5–8) moves to the empty limiting magnitude of the observation or location; other SQMs below 10 and NELMs above 8 are dropped. The placeholders of the old site (an observation SQM of -1 or 0, a limiting magnitude of 0) become null; `LegacyObservationsSeeder` no longer imports them. Run it after an SQL import.
- Repair the usernames of old messages (`App\Console\Commands\RepairMessageUsernames`): `php artisan messages:repair-usernames` (dry run; add `--apply` to write). The old site stored some senders/receivers in `messages` and the receivers of `messages_read`/`messages_deleted` HTML-encoded (`Torbj&ouml;rn`) or as UTF-8 read as Latin-1 (`TorbjÃ¶rn`), so the observer missed those messages and saw every old broadcast as unread. A name is only renamed when the repaired name is an account's username; names of deleted accounts stay encoded, so a new observer with that name does not inherit their messages. Run it after an SQL import.
- Delete the messages without a receiver (`App\Console\Commands\DeleteUnaddressedMessages`, the old site's achievement notices of 2015–2016, which no inbox shows) with their read/deleted marks: `php artisan messages:delete-unaddressed` (dry run; add `--apply` to delete). Run it after an SQL import.
- Delete the accounts that recorded nothing within 24 months after registration, as the privacy policy promises (`App\Console\Commands\PruneInactiveUsers`): `php artisan users:prune-inactive` (dry run; add `--apply` to send the warnings and delete, `--months=<n>` to change the period). Scheduled daily with `--apply`. The account gets an `InactiveAccountWarning` mail a month before (which fixes `users.inactivity_deletion_at`, at least a month after the mail) and a week before (`inactivity_final_warning_at`; a late run moves the date to a week after it); only an account that got both is deleted, and recording something clears both columns. Any row of the observer's own (observations, sessions or co-observing one, equipment, locations, lists, comments, likes, subscriptions, followed observers, sketches, sent messages, saved searches, report layouts, a login session) keeps the account; user 1, administrators and database experts are never deleted. Deletion goes through Jetstream's `DeleteUser`, which also removes the inbox, object metrics and table settings.
- Fill in the missing country of residence (`users.country`, an ISO code) of the observers (`App\Console\Commands\FillUserCountries`): `php artisan users:fill-country` (dry run; add `--apply` to write, `-v` to list them). A country name (old site) becomes its code; an empty country becomes the one `ObserverCountries::suggestFor()` finds: the top-level domain of the e-mail address (`.be`; generic domains such as `.com`, and country domains used like them such as `.io`, give nothing), else the country of most locations, else the standard location's, else that of most observations (a tie for "most" goes to the next rule). Scheduled daily with `--apply`, so an observer who clears the field gets it back.
- Send the daily digest of the observers someone follows (`App\Console\Commands\SendFollowDigest`): `php artisan follows:send-digest` (dry run; add `--apply` to send, `-v` to list them). Only for observers who turned on `users.follow_digest` on the profile page: one DeepskyLog message (and a mail if `sendMail`) in their language with the number of new observations per followed observer, nothing when there is nothing new. `users.follow_digest_sent_at` is when their last digest was made (also an empty one); the next covers the observations created since, at most a week. Scheduled daily at 07:00 with `--apply`.
- Regenerate translation files after adding new strings: `php artisan localize <lang>` (e.g. `nl`, `fr`, `de`, `es`, `sv`; comma-separate to do several at once). It scans `resources/views` for `__()`/`trans()`/`@lang()` and merges any new strings into `resources/lang/<lang>.json` with empty values, which then have to be translated by hand. Keys that are no longer used are kept unless you pass `--remove-missing`. The command is `app/Console/Commands/LocalizeCommand.php`, configured by `config/localize.php` — it is a local replacement for the abandoned `amirami/localizator` package (no Laravel 13 support), and reproduces its output byte for byte. Only the `<lang>.json` files are written: dotted short keys are deliberately discarded, because the short-key files in `resources/lang/<lang>/` (`observations.php`, `contrast.php`, …) are maintained by hand and a generator would both drop their comments and store interpolated keys such as `__("observations.visibility.$visKey")` literally. On a malformed `<lang>.json` the command aborts instead of overwriting it. Because it only scans views, strings in `app/`, `routes/` and `packages/` have to be added to the `<lang>.json` files by hand; `php scripts/scan_untranslated.php 'app,routes,resources/views,packages/socialstream/src'` lists every literal `__()`/`trans()`/`trans_choice()`/`@lang()` key without a translation in nl/fr/de/es/sv (as JSON, with the files that use it). `tests/Feature/LocalizeCommandTest.php` covers the command; `tests/Unit/LanguageFilesTest.php` guards that all language files stay parseable.
- Queue workers (background jobs like contrast-reserve/metrics computation): `php artisan queue:work --tries=3 --sleep=3 --timeout=60`. The PDF jobs (atlas, object sets, object reports) and the observation zips run for hours and go to the separate `database-long` connection (queue `long`, `retry_after` longer than their six-hour timeout, chosen by `queue.long_running` in `config/queue.php`), which needs a worker of its own: `php artisan queue:work database-long --sleep=3`. The constellation check of all objects on `/admin/check-objects` (`App\Jobs\CheckObjectConstellations`, about 4 minutes for 50,000 objects; result in the cache key `admin_check_objects:constellations`, all mismatches in `storage/app/object-checks/constellation-mismatches.csv`) uses that connection too. Restart both after deploys with `php artisan queue:restart`. `QUEUE_CONNECTION=database` by default — inspect failures with `php artisan queue:failed` / `queue:retry`.
- Common dev housekeeping: `php artisan storage:link`, `php artisan view:clear`, `php artisan migrate:fresh` (dev/test only, destroys data), `php artisan db:seed`.

## Architecture

- Laravel 12 / PHP 8.3, server-rendered with classical routing (`routes/web.php`, ~880 lines — the authoritative map from URL to Controller or Livewire component).
- **Livewire v4** (`app/Livewire/`) drives almost all interactive UI — data tables (`*Table.php`, built on `power-components/livewire-powergrid`), create/edit forms, search. Reusable form objects live in `app/Livewire/Forms`. Prefer Livewire server-driven UI over hand-written JS; JS is only used where Livewire genuinely can't do the job (e.g. Leaflet maps, TinyMCE, Flatpickr).
- **WireUI** supplies UI components/modals used throughout Blade views (`resources/views`).
- **Auth/teams**: Laravel Jetstream + `joelbutcher/socialstream` (vendored as a local path package in `packages/socialstream`, not on Packagist — edit it in place if needed). Every user belongs to a team: `Observers` (default), `Administrators`, `Database Experts`. Check roles via `$user->isAdministrator()`, `->isDatabaseExpert()`, `->isObserver()`, `->hasAdministratorPrivileges()`, and gate routes with policies (`app/Policies`) using ability strings like `->can('add_sketch', User::class)`. Registration (`App\Actions\Fortify\CreateNewUser`) allows usernames of letters, digits, spaces, `_ . -` (no `@`: login treats an email-like value as an email address). Observers delete their own account on the profile page (Jetstream `Features::accountDeletion()`, not shown to user 1); `App\Actions\Jetstream\DeleteUser` removes everything they recorded (observations with likes, comments and drawings, sessions, equipment, locations, lists), keeps the messages they sent, and refreshes the object statistics after the response — add new per-user tables there.
- **Domain model** (`app/Models`): observation-centric — `Observation`, `ObservationSession`, `DeepskyObject` (+ `CometObject`, `Asteroid`, `Planet`, `Moon`, `Star` for non-deep-sky targets), `Instrument`/`Eyepiece`/`Lens`/`Filter` (equipment, each with a `*Make`/`*Type` lookup model), `ObservingList` (+ items/comments/likes/subscriptions), `Location`, `Atlas`, `SketchOfTheMonth`/`Week`. Object naming/translation is split across `ObjectName`, `ObjectNames`, `ObjectNameTranslation`.
- **Astronomy calculations** (positions, magnitudes, ephemerides, coordinate transforms) come from the external `deepskylog/laravel-astronomy-library` package (in `vendor/`), not reimplemented in-app. `app/Services/EphemeridesBuilder.php` and the `ComputeEphemerides`/`ComputeContrastReserveFor*` jobs build on it. Comet positions and predicted magnitudes come from `app/Services/CometCoordinates.php`, which calculates them with the library from `comets_orbital_elements`: orbital elements of the Minor Planet Center where available, else JPL (`php artisan astronomy:updateOrbitalElements`), and the light curve of aerith.net in parts in the `light_curve` column, else H and n (`php artisan astronomy:updateCometPhotometry`; run it after the elements, it needs the perihelion of the current apparition); JPL Horizons is no longer queried (a query took 1–2 s, the calculation takes about 1 ms). Pass `$date->copy()` to the library's `calculate*Coordinates()` methods: versions before 6.8.1 move the date they are given. Asteroids work the same way with `app/Services/AsteroidCoordinates.php` (position and H-G magnitude from `asteroids_orbital_elements`, JPL's numbered asteroids, refreshed by the same command): observers add one on `/object/create/asteroid` (`Asteroid::addFromElements()`: named `(4) Vesta`, `asteroids.number` links it to its elements, the bare name is its designation and a search-index alias), and its observations are `target_type = 'solarsystem'`, `target_table = 'asteroids'`, keyed on its slug, as the OAL/CSV imports store them. Asteroid ids overlap with those of the other object tables, so `ObjectEphemerides` resolves them by the `sourceTypeRaw` hint and never through the `ComputeEphemerides` cache, and `AladinPreviewInfo` by its `object_type`. An asteroid is a point source, which Clark's contrast reserve cannot handle: `ContrastReserveCalculator::pointSource()` gives 0.4 × (telescopic limiting magnitude − predicted magnitude), in the same units and categories, at the magnification with the largest margin.
- **Star charts & atlas PDFs**: `app/Services/StarChartService.php` (large — renders SVG star charts, polar grids, star/DSO labeling) is the core rendering engine, driven by `app/Http/Controllers/AtlasController.php` and `StarChartController`/`NearbyExportController`. Full-atlas PDFs are generated asynchronously: the controller queues `App\Jobs\GenerateAtlasPdf`, which calls the controller's `renderAtlas()` internally, captures the PDF response, and writes status/results to cache (key `atlas_pdf:{token}`) and `storage/app/atlas/{token}.pdf` for polling/download. PDF rendering uses `barryvdh/laravel-dompdf`; Blade templates for this live in `resources/views/pdf/`. Object sets (`/object-sets`, linked from observing lists, search results and nearby objects) work the same way: the `ObjectSets` Livewire page queues `App\Jobs\GenerateObjectSetsPdf`, which uses `ObjectSetPdfService` to draw atlas-mode charts centred on each object, download DSS photos from STScI, and write `storage/app/object-sets/{token}.pdf` (status in cache key `object_sets_pdf:{token}`, kept 48 h). Object reports (`/object-report`, linked from the same places) are the old DeepskyLog "Report": the `ObjectReport` Livewire page edits a report layout (`report_layouts` table / `ReportLayout` model; `user_id` null = DeepskyLog default; fields and settings described in `ReportLayoutCatalog`) and queues `App\Jobs\GenerateObjectReportPdf`, which fills the fields with `ObjectReportDataBuilder` and draws the PDF with `ObjectReportPdfService` directly on dompdf's `Cpdf` (PDF points from the bottom left, Helvetica, as the old site did, so imported layouts print as before). All three PDF jobs extend `App\Jobs\QueuedPdfJob` (cache status, recent-PDF list, 48 h pruning, request locale carried into the worker, the requesting user logged in while rendering so charts show their seen/drawn markers, `failed()` marking a timed-out or killed job as failed). An observer may have at most `QueuedPdfJob::MAX_OPEN_PER_USER` PDFs (all kinds together) waiting or being made and ask for `MAX_PER_HOUR` an hour: code that queues one checks `refusal()` and calls `recordQueued()`, and puts the token in the kind's `recentKey()` list, which is what the open PDFs are counted from. `/downloads/mine` (Livewire `MyDownloads`, in the Downloads menu) lists the observer's PDFs and zip files of all kinds (`QueuedPdfJob::jobsFor()`) with until when a finished one can be downloaded (`expiresAt()`, `KEEP_HOURS` after `completed_at`), and removes a finished, failed or waiting one. When a job finishes or fails it queues `App\Jobs\NotifyQueuedPdfFinished` with a delay of `NOTIFY_DELAY_SECONDS` (on the default queue), which sends the observer a DeepskyLog message (and a mail if `sendMail`) in the language they asked in, unless a page showed them the result meanwhile: pages that show a job's status call `QueuedPdfJob::markSeen()`. A fatal error (out of memory) marks the job failed from a shutdown function, instead of hours later at `retry_after`; raise the memory limit with `App\Support\MemoryLimit::atLeast()`, never `ini_set()`, which would lower the worker's limit for every later job. A new kind gives its `kindLabel()` and `downloadRoute()`. `POST /downloads/dsl-atlas/generate` only renders a single page in the request; a whole atlas goes through the queue. The old layouts are imported with `php artisan db:seed --class=LegacyReportLayoutsSeeder`. Zips of observations with their drawings (`/observations/zip`, from the Export menu of the observation searches with `?q=` and the filters, or `?observer=` for all of one's own observations, linked on one's own `/drawings/{observer}`; an observer only gets their own observations, `ObservationZipController` adds `observer_id` to every source, administrators get anyone's) go the same way: the `ObservationZips` Livewire page queues `App\Jobs\GenerateObservationsZip` (a `QueuedPdfJob` with `extension()` `zip` that overrides `writeTo()`, as the zip does not fit in memory), and `App\Services\Observations\ObservationZipBuilder` writes `observations.xml` (OAL from `ObservationSearchExportController::oalWithImages()`, each drawing named in an `<image>` element), the original drawings uncompressed under `drawings/` (`drawingPath()` finds them on the public disk or in `public/images/{drawings,cometdrawings}`) and `drawings.csv`, at most `MAX_OBSERVATIONS`/`MAX_DRAWINGS` (one observer's 2,650 drawings are 2.1 GB, 15 s). The observation import (`/observation/import`, `ObservationImportController`) reads such a zip back (#817): `App\Services\Import\ImportDrawings` takes the one CSV/OAL file of a zip (or a CSV/OAL file with up to `MAX_LOOSE_DRAWINGS` images uploaded next to it), and the importers' `attachImportedDrawing()` copies the drawing an observation names (OAL `<image>`, a 16th CSV column) to the public disk under a name of its own; an observation that has a drawing keeps it, and the uploaded drawings no observation names are only reported.
- **Field views** (`/object/{slug}/field-views`, linked next to the Overview/Lookup/Detail charts; `ObjectFieldViewController`, Livewire `ObjectFieldViews`): the object with the naked eye (90°, zenith up, ground below the horizon), in the finder and in the telescope, for the observer's chosen instrument set (default a set with the standard telescope: the standard set when it has it, else the first that has it, else all equipment; it limits the telescopes, eyepieces, lenses and locations to its own, plus the finders mounted on its telescopes), telescope, eyepiece, lens, finder, location and moment: by default the moment the object is highest between the ends of astronomical (else nautical) twilight in the night of the ephemeris date, `FieldViewBuilder::highestAtNight()` (all kept in the query string; `/field-views.pdf` draws the same three views on A4). `App\Services\FieldViews\FieldViewBuilder` picks the equipment (default eyepiece: closest to the optimum detection magnification), takes the NELM of the location (or one from its SQM) and computes the limits with `App\Services\TelescopicLimitingMagnitude` less the extinction at the object's altitude, and the contrast reserve of the finder and telescope views at their magnification, with the object dimmed by that extinction (`not_visible` below the horizon); `FieldViewRenderer` draws each view as an SVG (objects with an outline in `object_contours` drawn with it, as on the charts; the target in red with its name) in a stereographic projection turned zenith up (alt-az mount, naked eye) or north up (equatorial mount) and mirrored per the instrument's flip/flop. A telescope's finder is `instruments.finder_id` and the lens always used with it (a coma corrector) `instruments.lens_id`, which replaced the observer's standard lens: `User::standardLensId()` is the lens of the standard telescope, used for the contrast reserve metrics (`Instrument` requeues them when that lens changes), the object page and the default lens of new observations; `instruments.field_of_view_deg` is the true field of a fixed-magnification instrument (else estimated as 50° / magnification). `php scripts/field_views_smoke.php <username> "<object>" <dir> '<json options>'` writes the SVGs of one object.
- **Tonight's best and lists for a night** (`App\Services\TonightsBest`): the objects worth observing in a night, well placed (at least 30°) in its dark hours (`App\Services\NightWindow`: end to begin of astronomical twilight, else nautical; its `highest()` gives an object's highest altitude analytically from the sidereal time). An observer with a standard telescope and location gets them from their stored contrast reserves (`user_object_metrics`, missing ones queued with `ObjectMetricsQueue`): mostly objects not yet seen with that telescope, a third challenging, a fifth seen ones at most, the objects of chosen catalogs/lists first, then the most observed (`object_observation_stats`), a few per type; guests and observers without that equipment get the most observed objects at `Location::forEphemerides()`; both get the planets and comets brighter than the telescope's reach (`TonightsBest::bodies()`, cached per night). Stars, double stars, quasars and supernovae are left out unless their type is chosen (`EXCLUDED_TYPES`), catalog errors always. Cached per observer, equipment, night and options until the observer records an observation. Shown on the home page (`x-tonights-best`, with a button that makes it an observing list, `observing-list.store-tonight`) and used by the wizard `/observing-lists/night` (Livewire `NightListWizard`: night, part of the night, kinds of objects (groups of deep-sky types, double stars, planets, comets), catalogs/lists first or only, seen objects, difficulty, number of deep-sky objects). Both lists hold the planets and comets as well, under their `search_index.name` (`list_name`), which the list tables match on. `ObservingList::createWithObjects()` makes a list from object names with a unique name. **The Moon**: `App\Services\MoonlightSky` brightens the sky at a point with the Krisciunas & Schaefer (1991) model from the Moon's phase, altitudes and distance; when the Moon is up, the contrast reserves of the candidates are recalculated with that sky (`ContrastReserveCalculator::calculate()` takes an `$sqm`) at the darkest moment the object is high enough. The stored metrics and every other contrast reserve stay those of a dark sky; the object page shows the one with the Moon of the ephemeris date next to it (`App\Services\MoonlitContrastReserve`, in `AladinPreviewInfo`).
- **Token API** (`/api/v1/me/...`, `App\Http\Controllers\Api\MeController`): read-only JSON on the data of the authenticated observer (profile, locations, equipment, instrument sets, observations with their deep-sky/comet details, sessions, observing lists with items), used by the `pydeepskylog` Python package. Routes need `auth:sanctum` plus `abilities:read`; observers make personal access tokens (Jetstream `Features::api()`, the only permission is `read`) on `/user/api-tokens` and send them as `Authorization: Bearer`. Observations and sessions are paginated (`per_page` ≤ 500). The public `/api/{instrument,eyepieces,lenses,filters}/{username}` endpoints stay as they are. `php scripts/me_api_smoke.php [username]` times every endpoint with a temporary token.
- **Countries**: `locations.country` holds the canonical English name of the `countries` table (where an observation was made; `Country::codeFor()` / `Country::nameForCode()` convert), `users.country` the ISO code of the observer's country of residence. `App\Services\ObserverCountries` serves the residence: the countries offered as a filter (`options()`, only those with at least `MIN_OBSERVERS` observers with observations, so a national ranking never points at one or two people), localized labels, `suggestFor()` and `usesInches()`. The residence ranks `/observers?country=`, gives the national rank on the observer page (`User::getCountryRanks()`), filters `/statistics?residence=` (a logged-in observer without parameters gets `?country=` of their own country; "All" sends an empty `country`), `/popular-objects`, `/popular-observations` and `/observing-lists/discover` (`?country=`), puts compatriots first in the co-observers of a session (`users.select.api?compatriots_first=1`), and is the starting country of a new location.
- **Messages** (`/messages`, `MessagesController`): rows of `messages` keyed by username (`receiver` `all` is a broadcast, one row for everybody); what a user read or deleted is a row in `messages_read`/`messages_deleted` (`receiver` = the user, also for the sender of a sent message). A message to several observers (at most `MessagesController::MAX_RECEIVERS`; the form's WireUI multiselect posts `receivers` as a JSON list, `receiver` takes one username, `?to=` on the form takes usernames separated by commas) is a copy per receiver with the same date. The inbox merges received messages with the sent ones, grouped per identical sender/subject/text/date (one row listing all receivers), and searches (`?q=`) and filters (`?box=received|sent`, `?unread=1`) in PHP before paginating. `reply_to_id` links a reply to the message it answers (shown on the message page); `message_blocks` (user ids) holds the observers a user blocked, whose messages and session invitations no longer reach them (administrators can't be blocked). `canRead()` decides who sees a message (receiver, everybody for a broadcast, sender, administrators). `Message::getNumberOfUnreadMails()` is the cached menu badge: create messages through the model so it is reset.
- **Objects seen in the same field** (#831): the form of a new deep-sky observation offers "Also seen in the same field": the objects of `objectpartof` and those within the true field of the equipment it starts with (`App\Services\Observations\SameFieldObjects::suggest()`, at most `MAX`), plus any object in a multiselect. `ObservationsController::store()` saves a copy of the observation for each (date, time, equipment, conditions, description and magnification; not the drawing or the object details) with `observations.seen_with_observation_id` set to the observation entered with the form; `Observation::seenInSameField()` gives the others of the group (they stay together when that one is deleted), shown on the detail page. Editing stays per observation.
- **Following observers** (`user_follows`, `App\Models\UserFollow`, `User::following()`/`followers()`): the Follow button on `/observers/{observer}` (`FollowController`; not yourself, not an observer who blocked you, and blocking someone ends their follow), the follower count there and, on one's own page, the lists of followers and followed observers. `User::followedObservations()` is the query behind the "Observers I follow" view of `/observations?following=1`, the daily digest and the personal RSS feed `/feed/following/{token}`, which is opened with the secret `users.follow_feed_token` instead of a login (made by `followFeedToken()`, renewed on that view; hidden from `toArray()`).
- **Sketch of the week / month** (`SketchOfTheWeek`, `SketchOfTheMonth`, chosen by administrators and database experts): a sketch of the week is chosen in the admin actions of an observation's detail page for a free Sunday from today on (`SketchOfTheWeek::freeSundays()`); the sketch of the month on `/sketch-of-the-month/create` (Livewire `ChooseSketchOfTheMonth`) for the 8th of a month without one (`SketchOfTheMonth::freeDates()`), from the sketches of the week of the month before (`candidates()`). The controllers' `store()` enforce these rules. A sketch chosen for a later date stays hidden until that date: public pages, counts and achievements use the `published()` scope or `isPublished()`. The observation search's drawing filter `not_sketch_of_the_week` finds the drawings that are no sketch of the week yet.
- **Complete catalogs** (#754, `complete_catalogs`, `App\Models\CompleteCatalog`): catalogs whose objects are all in DeepskyLog (M, NGC, IC, Caldwell, H400, H400-II, Arp, Hickson). Observers can't add an object to them: the create wizard leaves them out of its catalog list and `ObjectController::nameSearch()`/`store()` refuse the name, and the OAL observation import skips such a target (`CompleteCatalog::refusedCatalog()`, which matches "NGC 891" and "NGC891"). Administrators and database experts get a warning instead, and manage the list on `/admin/complete-catalogs` (Livewire `CompleteCatalogs`, ability `manage_catalogs`).
- **Search**: TNTSearch (`teamtnt/tntsearch`) indexes objects/observations; reindex via `php artisan search:reindex` whenever object data changes.
- **Observation/sketch cards** (`x-observation-deepsky`, `x-observation-comet`, `x-sketch-deepsky`, `x-sketch-comet`, `x-sketch`) read the observer, object, equipment, likes and same-day index from the request-scoped `App\Services\Observations\ObservationCardData`. A page that renders a list of cards calls `ObservationCardData::instance()->preload($observations)` first (in the controller or view), so each kind is fetched in one grouped query instead of per card; without it the cards still work, one query per distinct value. `php scripts/bench_card_queries.php [username]` counts the queries of the card pages. For observers with translation on, the cards never call Google Translate in the request (1–2 s a call): `App\Services\Observations\DescriptionTranslations::get()` returns the cached translation, else queues the observation, and one `TranslateObservationDescriptions` job per page translates them after the response (shown from the next view; needs a queue worker). `php scripts/bench_following.php <username> '<uri>' …` times pages through the HTTP kernel for a logged-in observer.
- **Caching**: `spatie/laravel-responsecache` caches full page responses; controllers/middleware that must always be fresh (e.g. search, per-user pages) opt out via `doNotCacheResponse`. Aggregate pages also cache their counts in the application cache, independently of the response cache and not cleared on changes: `/catalogs` for an hour, the RSS feeds for 15 minutes, and `/statistics`, `/popular-objects` (the whole ranking per mode, in `App\Services\PopularObjectsRanking`, which the PowerGrid `PopularObjectsTable` searches, sorts and pages) and `/observers` with `Cache::flexible()` (fresh for an hour; for a day after that the old counts are shown and recomputed after the response, by the `InvokeDeferredCallbacks` middleware in `app/Http/Kernel.php`, which `defer()` needs). Different objects (on `/observers`, `/statistics` and the observer pages) are counted on `observations.different_object_key`, a stored generated column holding `Observation::DIFFERENT_OBJECT_SQL`'s target, indexed per observer and per `target_type`; count on it rather than on an expression. Use `App\Support\SchemaColumns::has()` instead of `Schema::hasColumn()` in request code: it caches the column list (a day, forgotten after migrations). The Livewire component map of `AppServiceProvider` is cached in `bootstrap/cache/livewire-components.php` and rebuilt when a component directory changes. The observer statistics (`ComputeObserverStats`, `observer_stats:{id}`, 6 h) share the site-wide totals under `observer_stats:site_totals`, which a saved observation clears; for guests they are computed on the queue, never in the request.
- **Object metrics** (contrast reserve and best magnification in `user_object_metrics`): the optimum detection magnification is chosen with `ContrastReserveCalculator::bestMagnification()`, not the library's `calculateBestMagnification()` alone: only magnifications whose true field (from the eyepiece, else 50° / magnification) holds the object's major axis count, else the widest field, so a large object does not get the highest magnification. `SearchResultsTable` and `NearbyObjectsTable` never compute them in the request. `App\Services\ObjectMetricsQueue::queueMissing()` finds the objects without a metric in one query and dispatches `ComputeContrastReserveForObjectsBatch` (up to 1000 objects per job, equipment loaded once, one insert); the tables follow the job through a cache counter (`pending()`), so polling does not query. Without a queue worker the cells stay "…".
- **Background jobs** (`app/Jobs`): per-user/per-object metrics (contrast reserve, observer stats), session-invitation email, the notification mails of messages and broadcasts (`App\Mail\MessageReceived` is `ShouldQueue`; send it with `->locale($recipient->language)`, the worker doesn't know the request's language), description translation, and atlas PDF generation. These are dispatched onto the `database` queue and require a running `queue:work` process to actually execute — commands that "queue" work will silently do nothing without a worker.
- **Ad-hoc/debug scripts**: `deepskylog/scripts/` holds standalone PHP scripts (run with `php scripts/xxx.php`, bootstrapping Laravel themselves) used for manual testing of chart/PDF rendering, cache table inspection, etc. — not part of the app runtime, safe to add to but not to treat as tested code paths.
- **User HTML**: rich text written in TinyMCE (observation and equipment/location descriptions, profile `about`, session weather/equipment/comments, messages) is printed with `{!! \App\Support\Html::purify($text, true) !!}` (the `true` decodes the entity-encoded markup of old rows first); the models also purify it on save with the `App\Casts\PurifiedHtml` cast. Names and other plain text go through `{{ }}` / `e()`, with `html_entity_decode()` inside, never in `{!! !!}`. CSV/XLSX exports escape cells a spreadsheet would read as a formula with `App\Support\SpreadsheetCell` (PowerGrid's exporters are replaced by `App\Support\Exports\*` in `config/livewire-powergrid.php`). PowerGrid prints every field unescaped: `->add('field')` without a closure escapes, but a closure must call `e()` itself.
- **Logs**: `storage/logs/laravel-YYYY-MM-DD.log` (daily rotation).
