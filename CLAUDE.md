# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

This is a monorepo. The Laravel application lives entirely in `deepskylog/` — run all commands below from that directory. The repo root also contains `3d-print/` (unrelated OpenSCAD/3D-print assets for physical hardware) and top-level docs (`README.md`, `Tips.md`, `CONTRIBUTING.md`).

## Commands

All commands run from `deepskylog/`.

- Install PHP deps: `composer install` (PHP 8.3 required); update with `composer update`.
- Install/build frontend: `npm install`, then `npm run dev` (Vite dev server) or `npm run build` (production).
- Format frontend/Blade: `npm run format` (Prettier with the Blade plugin, writes `resources/`).
- Format PHP: `laravel/pint` or `friendsofphp/php-cs-fixer` (config in `.php-cs-fixer.dist.php`, PSR-12 + short array syntax + alphabetized imports).
- Run tests: `php artisan test` (Pest, with `pestphp/pest-plugin-laravel`). Run a single test file with `php artisan test tests/Feature/SomeTest.php` or filter by name with `php artisan test --filter=testName`. Test env uses in-memory SQLite, sync queue, array cache/session (see `phpunit.xml`) — no external services needed. `tests/TestCase.php` binds `Tests\Support\CaseInsensitiveBlueprint`, which gives every SQLite string column `COLLATE NOCASE`, so `=` compares case-insensitively like the `utf8mb4_unicode_ci` columns on MariaDB: compare plain columns (`where('name', $v)`), not `LOWER(name) = ?`, which keeps MariaDB from using the index. An expression such as `COALESCE(a, b)` or `REPLACE(a, …)` has no collation in SQLite, so comparisons on those still need `LOWER()` on both sides.
- Rebuild search index after object data changes: `php artisan search:reindex` (TNTSearch).
- Rebuild the per-object observation statistics (`object_observation_stats`, `object_observation_stats_by_observer`: the seen/last seen columns of the object tables, via `App\Services\ObjectObservationStatistics`): `php artisan observations:rebuild-object-stats`. `ObservationObserver` keeps them up to date on model saves; code that changes `observations` with a mass update must call `ObjectObservationStatistics::refreshObjects()`, and after an SQL import or repair run the command.
- Rename observing list items to the canonical object names the list tables match on (`App\Services\ObservingListItemNameResolver`): `php artisan observing-lists:normalize-items` (dry run; add `--apply` to write, `--list=<id>` to limit). Items matching no object are only reported.
- Remove the M 1 the import of the old observing lists (April 2026) put first in about 200 lists it does not belong to (`App\Console\Commands\RemoveSpuriousListItems`): `php artisan observing-lists:remove-spurious-items` (dry run; add `--apply` to write, `-v` to list the lists). Lists whose name says M 1 belongs there (Messier, Crab, supernova remnants) are only listed; a list left empty is deleted unless it has comments, likes or subscribers. Run it after an SQL import.
- Add the member galaxies of the Hickson compact groups (`App\Console\Commands\ImportHicksonMembers`, from `database/hickson_galaxies.csv`, Hickson 1989 / VizieR VII/213): `php artisan objects:import-hickson-members` (dry run; add `--apply` to write). A member becomes the alternative name `Hickson 11A` of the galaxy with its NGC/IC/UGC name, else of the nearest galaxy within 20" (better known catalogs first), else a new galaxy `Hickson 11A`, linked to its group in `objectpartof`. Members whose galaxy is already another member are only listed.
- Add the traditional names of the Struve double stars (#480, `App\Console\Commands\AddStruveSigmaNames`, logic in `App\Services\StruveSigmaNames`): `php artisan objects:add-struve-sigma-names` (dry run; add `--apply` to write, `-v` to list them). The objects of CLANB, ENRNN, ENSTR, RNHII and STNEB get the type `OBJECT_TYPES` gives them (M 17 → HII, NGC 2264 → OPNCL, NGC 1999 → REFNB, …), else the default of `REMOVED_TYPES`, in `objects` and `search_index`; the types are deleted from `deepskytypes` and `target_types`, and the test object Hickson 752 is deleted. Run it after an SQL import.

## Architecture

- Laravel 12 / PHP 8.3, server-rendered with classical routing (`routes/web.php`, ~880 lines — the authoritative map from URL to Controller or Livewire component).
- **Livewire v4** (`app/Livewire/`) drives almost all interactive UI — data tables (`*Table.php`, built on `power-components/livewire-powergrid`), create/edit forms, search. Reusable form objects live in `app/Livewire/Forms`. Prefer Livewire server-driven UI over hand-written JS; JS is only used where Livewire genuinely can't do the job (e.g. Leaflet maps, TinyMCE, Flatpickr).
- **WireUI** supplies UI components/modals used throughout Blade views (`resources/views`).
- **Auth/teams**: Laravel Jetstream + `joelbutcher/socialstream` (vendored as a local path package in `packages/socialstream`, not on Packagist — edit it in place if needed). Every user belongs to a team: `Observers` (default), `Administrators`, `Database Experts`. Check roles via `$user->isAdministrator()`, `->isDatabaseExpert()`, `->isObserver()`, `->hasAdministratorPrivileges()`, and gate routes with policies (`app/Policies`) using ability strings like `->can('add_sketch', User::class)`. Registration (`App\Actions\Fortify\CreateNewUser`) allows usernames of letters, digits, spaces, `_ . -` (no `@`: login treats an email-like value as an email address). Observers delete their own account on the profile page (Jetstream `Features::accountDeletion()`, not shown to user 1); `App\Actions\Jetstream\DeleteUser` removes everything they recorded (observations with likes, comments and drawings, sessions, equipment, locations, lists), keeps the messages they sent, and refreshes the object statistics after the response — add new per-user tables there.
- **Domain model** (`app/Models`): observation-centric — `Observation`, `ObservationSession`, `DeepskyObject` (+ `CometObject`, `Asteroid`, `Planet`, `Moon`, `Star` for non-deep-sky targets), `Instrument`/`Eyepiece`/`Lens`/`Filter` (equipment, each with a `*Make`/`*Type` lookup model), `ObservingList` (+ items/comments/likes/subscriptions), `Location`, `Atlas`, `SketchOfTheMonth`/`Week`. Object naming/translation is split across `ObjectName`, `ObjectNames`, `ObjectNameTranslation`.
- **Astronomy calculations** (positions, magnitudes, ephemerides, coordinate transforms) come from the external `deepskylog/laravel-astronomy-library` package (in `vendor/`), not reimplemented in-app. `app/Services/EphemeridesBuilder.php` and the `ComputeEphemerides`/`ComputeContrastReserveFor*` jobs build on it. Comet positions and predicted magnitudes come from `app/Services/CometCoordinates.php`, which calculates them with the library from `comets_orbital_elements`: orbital elements of the Minor Planet Center where available, else JPL (`php artisan astronomy:updateOrbitalElements`), and the light curve of aerith.net in parts in the `light_curve` column, else H and n (no magnitude without a plausible n: `CometCoordinates::photometry()`) (`php artisan astronomy:updateCometPhotometry`; run it after the elements, it needs the perihelion of the current apparition); JPL Horizons is no longer queried (a query took 1–2 s, the calculation takes about 1 ms). Pass `$date->copy()` to the library's `calculate*Coordinates()` methods: versions before 6.8.1 move the date they are given. Asteroids work the same way with `app/Services/AsteroidCoordinates.php` (position and H-G magnitude from `asteroids_orbital_elements`, JPL's numbered asteroids, refreshed by the same command): observers add one on `/object/create/asteroid` (`Asteroid::addFromElements()`: named `(4) Vesta`, `asteroids.number` links it to its elements, the bare name is its designation and a search-index alias), and its observations are `target_type = 'solarsystem'`, `target_table = 'asteroids'`, keyed on its slug, as the OAL/CSV imports store them. Asteroid ids overlap with those of the other object tables, so `ObjectEphemerides` resolves them by the `sourceTypeRaw` hint and never through the `ComputeEphemerides` cache, and `AladinPreviewInfo` by its `object_type`. An asteroid is a point source, which Clark's contrast reserve cannot handle: `ContrastReserveCalculator::pointSource()` gives 0.4 × (telescopic limiting magnitude − predicted magnitude), in the same units and categories, at the magnification with the largest margin.
- **Star charts & atlas PDFs**: `app/Services/StarChartService.php` (large — renders SVG star charts, polar grids, star/DSO labeling) is the core rendering engine, driven by `app/Http/Controllers/AtlasController.php` and `StarChartController`/`NearbyExportController`. Full-atlas PDFs are generated asynchronously: the controller queues `App\Jobs\GenerateAtlasPdf`, which calls the controller's `renderAtlas()` internally, captures the PDF response, and writes status/results to cache (key `atlas_pdf:{token}`) and `storage/app/atlas/{token}.pdf` for polling/download. PDF rendering uses `barryvdh/laravel-dompdf`; Blade templates for this live in `resources/views/pdf/`. Object sets (`/object-sets`, linked from observing lists, search results and nearby objects) work the same way: the `ObjectSets` Livewire page queues `App\Jobs\GenerateObjectSetsPdf`, which uses `ObjectSetPdfService` to draw atlas-mode charts centred on each object, download DSS photos from STScI, and write `storage/app/object-sets/{token}.pdf` (status in cache key `object_sets_pdf:{token}`, kept 48 h). Object reports (`/object-report`, linked from the same places) are the old DeepskyLog "Report": the `ObjectReport` Livewire page edits a report layout (`report_layouts` table / `ReportLayout` model; `user_id` null = DeepskyLog default; fields and settings described in `ReportLayoutCatalog`) and queues `App\Jobs\GenerateObjectReportPdf`, which fills the fields with `ObjectReportDataBuilder` and draws the PDF with `ObjectReportPdfService` directly on dompdf's `Cpdf` (PDF points from the bottom left, Helvetica, as the old site did, so imported layouts print as before). All three PDF jobs extend `App\Jobs\QueuedPdfJob` (cache status, recent-PDF list, 48 h pruning, request locale carried into the worker, the requesting user logged in while rendering so charts show their seen/drawn markers, `failed()` marking a timed-out or killed job as failed). An observer may have at most `QueuedPdfJob::MAX_OPEN_PER_USER` PDFs (all kinds together) waiting or being made and ask for `MAX_PER_HOUR` an hour: code that queues one checks `refusal()` and calls `recordQueued()`, and puts the token in the kind's `recentKey()` list, which is what the open PDFs are counted from. `/downloads/mine` (Livewire `MyDownloads`, in the Downloads menu) lists the observer's PDFs and zip files of all kinds (`QueuedPdfJob::jobsFor()`) with until when a finished one can be downloaded (`expiresAt()`, `KEEP_HOURS` after `completed_at`), and removes a finished, failed or waiting one. When a job finishes or fails it queues `App\Jobs\NotifyQueuedPdfFinished` with a delay of `NOTIFY_DELAY_SECONDS` (on the default queue), which sends the observer a DeepskyLog message (and a mail if `sendMail`) in the language they asked in, unless a page showed them the result meanwhile: pages that show a job's status call `QueuedPdfJob::markSeen()`. A fatal error (out of memory) marks the job failed from a shutdown function, instead of hours later at `retry_after`; raise the memory limit with `App\Support\MemoryLimit::atLeast()`, never `ini_set()`, which would lower the worker's limit for every later job. A new kind gives its `kindLabel()` and `downloadRoute()`. `POST /downloads/dsl-atlas/generate` only renders a single page in the request; a whole atlas goes through the queue. The old layouts are imported with `php artisan db:seed --class=LegacyReportLayoutsSeeder`. Zips of observations with their drawings (`/observations/zip`, from the Export menu of the observation searches with `?q=` and the filters, or `?observer=` for all of one's own observations, linked on one's own `/drawings/{observer}`; an observer only gets their own observations, `ObservationZipController` adds `observer_id` to every source, administrators get anyone's) go the same way: the `ObservationZips` Livewire page queues `App\Jobs\GenerateObservationsZip` (a `QueuedPdfJob` with `extension()` `zip` that overrides `writeTo()`, as the zip does not fit in memory), and `App\Services\Observations\ObservationZipBuilder` writes `observations.xml` (OAL from `ObservationSearchExportController::oalWithImages()`, each drawing named in an `<image>` element), the original drawings uncompressed under `drawings/` (`drawingPath()` finds them on the public disk or in `public/images/{drawings,cometdrawings}`) and `drawings.csv`, at most `MAX_OBSERVATIONS`/`MAX_DRAWINGS` (one observer's 2,650 drawings are 2.1 GB, 15 s). The observation import (`/observation/import`, `ObservationImportController`) reads such a zip back (#817): `App\Services\Import\ImportDrawings` takes the one CSV/OAL file of a zip (or a CSV/OAL file with up to `MAX_LOOSE_DRAWINGS` images uploaded next to it), and the importers' `attachImportedDrawing()` copies the drawing an observation names (OAL `<image>`, a 16th CSV column) to the public disk under a name of its own; an observation that has a drawing keeps it, and the uploaded drawings no observation names are only reported. An OAL file whose targets are not all in the database is not imported at once (#221): `OalObservationImporter::newTargets()` lists the targets the file defines well enough to add, with the objects near them (`App\Services\NearbyObjects`, shared with the coordinate check of a new object) and the one of the same type that is probably the target; the upload is kept on the local disk under `observation-imports/{token}` (`KEEP_HOURS`, details in the cache key `observation_import:{token}`) while the observer chooses on `/observation/import/{token}/objects` for each target: an object DeepskyLog has, a new object, or skip it (`withObjectChoices()`). A CSV import never adds objects.
- **Field views** (`/object/{slug}/field-views`, linked next to the Overview/Lookup/Detail charts; `ObjectFieldViewController`, Livewire `ObjectFieldViews`): the object with the naked eye (90°, zenith up, ground below the horizon), in the finder and in the telescope, for the observer's chosen instrument set (default a set with the standard telescope: the standard set when it has it, else the first that has it, else all equipment; it limits the telescopes, eyepieces, lenses and locations to its own, plus the finders mounted on its telescopes), telescope, eyepiece, lens, finder, location and moment: by default the moment the object is highest between the ends of astronomical (else nautical) twilight in the night of the ephemeris date, `FieldViewBuilder::highestAtNight()` (all kept in the query string; `/field-views.pdf` draws the same three views on A4). `App\Services\FieldViews\FieldViewBuilder` picks the equipment (default eyepiece: closest to the optimum detection magnification), takes the NELM of the location (or one from its SQM) and computes the limits with `App\Services\TelescopicLimitingMagnitude` less the extinction at the object's altitude, and the contrast reserve of the finder and telescope views at their magnification, with the object dimmed by that extinction (`not_visible` below the horizon); `FieldViewRenderer` draws each view as an SVG (objects with an outline in `object_contours` drawn with it, as on the charts; the target in red with its name) in a stereographic projection turned zenith up (alt-az mount, naked eye) or north up (equatorial mount) and mirrored per the instrument's flip/flop. A telescope's finder is `instruments.finder_id` and the lens always used with it (a coma corrector) `instruments.lens_id`, which replaced the observer's standard lens: `User::standardLensId()` is the lens of the standard telescope, used for the contrast reserve metrics (`Instrument` requeues them when that lens changes), the object page and the default lens of new observations; `instruments.field_of_view_deg` is the true field of a fixed-magnification instrument (else estimated as 50° / magnification). `php scripts/field_views_smoke.php <username> "<object>" <dir> '<json options>'` writes the SVGs of one object.
- **Tonight's best and lists for a night** (`App\Services\TonightsBest`): the objects worth observing in a night, well placed (at least 30°) in its dark hours (`App\Services\NightWindow`: end to begin of astronomical twilight, else nautical; its `highest()` gives an object's highest altitude analytically from the sidereal time). An observer with a standard telescope and location gets them from their stored contrast reserves (`user_object_metrics`, missing ones queued with `ObjectMetricsQueue`): mostly objects not yet seen with that telescope, a third challenging, a fifth seen ones at most, the objects of chosen catalogs/lists first, then the most observed (`object_observation_stats`), a few per type; guests and observers without that equipment get the most observed objects at `Location::forEphemerides()`; both get the planets and comets brighter than the telescope's reach (`TonightsBest::bodies()`, cached per night). The deep-sky objects are spread over the hours chosen: `pick()` takes each next one from the part of about two hours (at most five) with the fewest so far, so the most observed objects that stand highest at the start of the dark hours don't fill the list. Stars, double stars, quasars and supernovae are left out unless their type is chosen (`EXCLUDED_TYPES`), catalog errors always. Cached per observer, equipment, night and options until the observer records an observation. Shown on the home page (`x-tonights-best`, with a button that makes it an observing list, `observing-list.store-tonight`) and used by the wizard `/observing-lists/night` (Livewire `NightListWizard`: night, part of the night, kinds of objects (groups of deep-sky types, double stars, planets, comets), catalogs/lists first or only, seen objects, difficulty, number of deep-sky objects). Both lists hold the planets and comets as well, under their `search_index.name` (`list_name`), which the list tables match on. `ObservingList::createWithObjects()` makes a list from object names with a unique name. **The Moon**: `App\Services\MoonlightSky` brightens the sky at a point with the Krisciunas & Schaefer (1991) model from the Moon's phase, altitudes and distance; when the Moon is up, the contrast reserves of the candidates are recalculated with that sky (`ContrastReserveCalculator::calculate()` takes an `$sqm`) at the darkest moment the object is high enough. The stored metrics and every other contrast reserve stay those of a dark sky; the object page shows the one with the Moon of the ephemeris date next to it (`App\Services\MoonlitContrastReserve`, in `AladinPreviewInfo`).

- **Object metrics** (contrast reserve and best magnification in `user_object_metrics`): the optimum detection magnification is chosen with `ContrastReserveCalculator::bestMagnification()`, not the library's `calculateBestMagnification()` alone: only magnifications whose true field (from the eyepiece, else 50° / magnification) holds the object's major axis count, else the widest field, so a large object does not get the highest magnification. The object is dimmed by the atmospheric extinction (`App\Services\AtmosphericExtinction`, 0.25 mag per air mass against the zenith, Kasten & Young) at its highest altitude at the location (`ContrastReserveCalculator::highestAltitude()`, 90° − |latitude − declination|; pass `altitude:` to `calculate()`/`pointSource()`): an object that never rises is stored as `not_visible` without a contrast reserve, and a change of a location's latitude deletes its metrics. `SearchResultsTable` and `NearbyObjectsTable` never compute them in the request. `App\Services\ObjectMetricsQueue::queueMissing()` finds the objects without a metric in one query and dispatches `ComputeContrastReserveForObjectsBatch` (up to 1000 objects per job, equipment loaded once, one insert); the tables follow the job through a cache counter (`pending()`), so polling does not query. Without a queue worker the cells stay "…".
